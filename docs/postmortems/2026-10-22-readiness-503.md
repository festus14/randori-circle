# Postmortem: readiness 503 on the first activation join (2026-10-22)

## Summary

On 2026-10-22 the first invitee joined through password sign-up with
email activation. That join path records `activation.verified`, a
provenance the membership-readiness evaluator did not recognise, so
the account counted as unproven and `/api/health/ready` returned 503
for about 1 hour 38 minutes. The fix (#349, ID-84) taught the
evaluator the third provenance. A follow-up (#351, ID-85) the same
day removed a second readiness hazard found while reviewing account
deletion: the migration runner judged managed databases by the
one-time adoption rule.

## Impact

- **Duration:** 07:20–08:58 UTC (about 1 hour 38 minutes), confirmed
  by the readiness probe returning 200 after the #349 deploy.
- **What members saw:** the readiness probe failed, and pairing
  readiness (`requireClosedMembership`) failed with it. The
  invitee's join itself succeeded — the account, membership, and
  invitation consumption were created correctly in one transaction;
  the probe misclassified the account afterwards.
- **What members did not lose:** no data loss, no lost membership,
  no leaked data. No database row needed repair; the fix changed
  only the evaluator.
- **Scope:** readiness-gated flows for the whole service while the
  probe failed.

## Detection

The outage was observed on the day (see
[#361](https://github.com/festus14/randori-circle/issues/361):
"Today's readiness outage … showed there is no quick triage path").
No watchdog fired on it: the outbox and backup watchdogs do not
observe readiness, and the readiness endpoint itself returns the
same 503 body for every blocker family, so there was no signal
naming the cause. The triage gap is itself a finding — it is why
#361 added the [readiness-503 runbook](../runbooks/readiness-503.md).

## Root cause

`db/membership-readiness.js` accepted only two account provenances:
a `membership.backfilled` audit event or an `invitation.accepted`
audit event. Password sign-up through email activation is a third
join path: `verifyEmailActivation` atomically creates the new
account, consumes the invitation and the activation, inserts the
active membership, and records `activation.verified` — never
`invitation.accepted`. The new account therefore counted as
`invalidAccountProvenance`, and the evaluator pushed the
`closed_rollout_account_audit_invalid` blocker.

Contributing factor: no test exercised a join via activation against
readiness before this incident. The #349 tests fail against the
pre-fix code and pass with it — the coverage gap was in the join-path
matrix, not in any one evaluator.

A second, latent hazard was found the same day while reviewing
account deletion (#347): `db/migration-runner.js` judged even a
managed database with the one-time adoption rule
(`inspectMembershipAdoptionReadiness`), which requires every
non-demo account to have an active primary membership. As soon as an
owner removed or deactivated a member, or a member left, a no-op
`applyMigrations` threw `MIGRATION_SCHEMA_INVALID` and the backup
rehearsal failed in evidence detection and collection — while health
and pairing readiness, which already used the steady-state rule,
stayed green and warned of nothing.

## Fix

- **#349 (ID-84), no migration, no flag.** Both
  `inspectCompletedMembershipRollout` and
  `inspectMembershipAdoptionReadiness` accept a third provenance: a
  used, unrevoked primary-circle invitation with `used_by=account`,
  joined to its consumed `auth_email_activations` row (same circle,
  `used_at IS NOT NULL`), and an `activation.verified` audit in that
  circle with actor = subject = account, `invitation_id` = that
  invitation, and dedupe key
  `activation-verified:<activation id>`. A new
  `malformedActivationAudits` count is a
  `closed_rollout_account_audit_invalid` blocker in both evaluators:
  any `activation.verified` event whose invitation, activation,
  account (missing or demo), actor, circle, or dedupe key does not
  line up fails closed. That is safe as a blocker because
  `verifyEmailActivation` is the only writer, runs in one
  transaction, and only creates new accounts. The activation ledger
  arrived in schema v7 and the migration runner inspects adoption
  from v2, so each evaluator checks `sqlite_schema` first; if the
  table is absent, every `activation.verified` event counts as
  malformed. The migration runner's adoption evidence fingerprint
  was deliberately unchanged. Recovery if the fix regressed: revert
  the commit — readiness then fails again for every account that
  joined by activation, which is exactly the fail-closed behaviour.
- **#351 (ID-85), no migration, no flag.** `inspectMembershipAdoption`
  now uses the steady-state check for a managed ledger (the
  completed steady-state check once the rollout is closed, the
  pristine-open check before), and `inspectMigrationState` passes
  `managed` for managed ledgers. Adopting an unmanaged database
  keeps the strict rule, uncovered accounts included. All
  steady-state invariants still block: provenance, malformed audits,
  active owner, backfill completion, orphan memberships.

Verification of both fixes: new unit tests on real migrated SQLite
(#349: `tests/unit/membership-activation-provenance.test.mjs`;
#351: `tests/unit/migration-steady-state-readiness.test.mjs`),
both failing on the pre-fix code and passing with it, plus full
`test:unit` and the `check:*` scripts green at merge time.

## What went well / what went wrong

- Went well: the probe failed closed instead of serving traffic on
  a misjudged membership state; the join itself was atomic and
  needed no data repair; the fix was small, flag-free, and
  migration-free; the review of a neighbouring change (#347) caught
  the second hazard (#351) the same day.
- Went wrong: a production join path was not covered against
  readiness before launch; the readiness endpoint names no blocker,
  so triage had no quick path; no alert observes readiness, so
  detection depended on observation; the adoption/steady-state
  distinction lived in two evaluators with different callers, so a
  rule that was safe for health was silently wrong for migrations.

## Prevention

- One readiness test per join path (backfill, invitation acceptance,
  activation) — done in #349; future join paths must add theirs.
- The [readiness-503 runbook](../runbooks/readiness-503.md) records
  how to tell schema/ledger, key-control, and membership-provenance
  blockers apart, including the two distinctions this incident
  taught: uncovered accounts do not take steady-state health offline,
  and activation provenance is a third valid form.
- The adoption/steady-state rule split is recorded in ID-85; any
  future readiness rule change must state which evaluator(s) it
  touches and why.
